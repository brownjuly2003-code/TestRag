# Opus Result Next: Synthetic-Content Disclaimer Pack

> Контекст риска: R4 в `opus_result_risks.md` — synthetic-only corpus может быть принят за реальные регламенты заказчика. `manifests/MANIFEST.md §header` уже фиксирует, что все документы с `source_type: synthetic_internal` созданы для демонстрации.
> Назначение: готовые формулировки для (а) демо-слайдов, (б) ответов Telegram-бота, (в) README. Без правок проект-файлов.
> Тон: нейтральный, без юридических обещаний. Все варианты совместимы с `docs/legal-document-prompts.md §Безопасность и подача`.

## Общая логика

Два уровня раскрытия:

1. **Уровень корпуса (synthetic-internal):** «политики/регламенты в индексе — демонстрационные, не корпоративные документы заказчика».
2. **Уровень нормативной базы (внешние ссылки):** «ссылки на ТК/ГК/ФЗ — реальные нормативные акты, но redirect/citation требует проверки юристом перед применением».

Эти два уровня **разные**. Не сводить в одну фразу «всё демо», иначе теряется ценность нормативного грунта.

## 2. Ответы Telegram-бота

### Вариант A — постфикс к каждому ответу (рекомендуется)

Однострочник, добавляется в конец каждого ответа RAG API. Помещается в SMS-режим:

```
ℹ️ Демо-режим: документы корпуса — синтетические, нормативные ссылки реальные. Не юридическая консультация.
```

Без emoji (если по бренду нельзя):

```
[Демо-режим: документы корпуса — синтетические, нормативные ссылки реальные. Не юридическая консультация.]
```

### Вариант B — для intent=template_draft (усиленный)

К любому ответу с `intent=template_draft` или `requires_human_review=true`:

```
⚠️ Черновик подготовлен автоматически и требует проверки HR/юристом до подписания.
Корпус документов — демонстрационный (synthetic_internal). Финальные реквизиты,
основания и формулировки сверять с действующими корпоративными регламентами.
```

Без emoji:

```
[Требует проверки HR/юристом] Черновик подготовлен автоматически.
Корпус документов — демонстрационный. Финальные реквизиты, основания и
формулировки сверять с корпоративными регламентами.
```

### Вариант C — pinned-сообщение в чате бота (одноразовый старт)

При первом контакте пользователя (или при `/start`):

```
Привет. Я — демо-ассистент по HR и юридическим вопросам.

Что важно знать:
• Документы в моей базе — синтетические образцы для демо, не корпоративные регламенты.
• Ссылки на ТК РФ, ГК РФ, ФЗ — реальные. Но конкретный ответ всегда сверяйте с юристом.
• Я могу подготовить черновик документа, но финальную версию должны утвердить HR/юрист.
• Если уверенности недостаточно — я честно отказываюсь отвечать.

Это не юридическая консультация.
```

### Вариант D — refusal с упоминанием sample-state (когда `chunk_count` мал)

Когда `refused=true` ИЗ-ЗА того, что корпус ещё не доукомплектован (а не из-за OOD-темы), добавлять:

```
Недостаточно данных в проиндексированной демо-базе. В production-конфигурации
с полным корпусом регламентов покрытие шире. Уточните формулировку или
переформулируйте через номер статьи/документа.
```

## 3. README (project-level)

### Блок для шапки (после §MVP, до §Архитектура)

```markdown
## Демонстрационный характер корпуса

Корпус `corpus/` содержит **синтетические** документы (политики, шаблоны,
типовые договоры, претензии, FAQ), помеченные в `manifests/MANIFEST.md`
тегом `source_type: synthetic_internal`. Они созданы исключительно для
демонстрации работы RAG-пайплайна и **не являются** корпоративными
регламентами какой-либо организации.

Нормативные источники (`manifests/NORMATIVE_SOURCE_MANIFEST.md`) — реальные
акты (ТК РФ, ГК РФ, 152-ФЗ, 98-ФЗ, 259-ФЗ, CMR, приказы Минтранса). Цитирование
статей проверяется по этому реестру.

В production-внедрении synthetic-документы заменяются на регламенты заказчика
(ingestion через тот же pipeline). Любые автоматически сгенерированные
черновики (intent `template_draft`) требуют проверки HR/юристом перед
использованием.

Demo не является юридической консультацией.
```
